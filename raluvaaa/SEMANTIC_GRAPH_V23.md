# RALUVAAA V23 - Semantic graph contract

## Purpose

Preserve the approved V03 visual language while making every visible branch and meaningful node correspond to the actual product grammar of a wish.

This document is the semantic contract for the next population pass.

## Core rule

**One root wish = one lineage.**

A lineage is the visible history and descendants of one original intention. It is not a person profile and it is not a thematic cluster.

A human can own several completely independent lineages. They are linked to the same private identity in data, but they are not automatically placed together or visually connected.

## Identity relation

Each lineage stores a private `owner_id` / `wisher_id` reference.

That reference is used for rights, claim, editing, Bloom confirmation, Let go and later notifications. It is not a public profile node and does not affect graphical position.

## Meaning of visible structures

### CREATE

Creates a new independent lineage. The first meaningful point is the original wish.

### PIVOT

Changes the direction of the same wish while preserving its earlier path as history.

A pivot does not create an unrelated child wish. Visually it should bend or fork the continuing trajectory while the earlier direction remains as a trace.

### SPLIT

Creates real child wishes / sub-intentions from a wish node.

Children remain inside the same lineage. Any child can itself SPLIT again, recursively.

### BLOOM

Marks a wish or sub-wish as accomplished, confirmed only by the wisher.

Bloom does not erase the branch. It creates the strongest flowering state. Over time the flower can soften / patinate into a durable accomplished trace while remaining visible.

### LET GO

Marks a wish or sub-wish as voluntarily abandoned by the wisher.

It does not disappear. It becomes a quieter, dormant / fossil trace distinct from Bloom.

### ENCOURAGE

Injects energy into a wish. It does not create topology and it does not automatically imply progress or completion.

The persistent aggregate can subtly affect light / breathing, while the act itself can generate a short pulse.

### HELP

A concrete human contribution attached to a wish or sub-wish.

Help is persistent and should be visually distinct from simple encouragement. Preferred visual metaphor: small leaves / buds / partial flowering around the targeted branch or node.

HELP is an antechamber to Bloom visually, not semantically. No quantity of help may automatically declare Bloom. Final Bloom always belongs to the wisher.

Help can have scope:
- `node`: help aimed at a specific wish or sub-wish;
- `lineage`: general help that supports the broader intention.

### CONNECT / CARRY

Creates a relationship between two independent lineages.

It is not a biological parent-child edge and must not visually look like a normal branch. Preferred representation: a distinct warp / bridge, curved or iridescent, connecting the relevant points while both lineages remain independent.

A connection may later result in HELP or mutual help, but CONNECT itself only states that a meaningful relationship exists.

## Meaningful nodes vs rendering geometry

The product must distinguish:

1. **semantic nodes**: original wish, child / sub-wish, current pivot state, Bloomed or Let-go target;
2. **rendering control points**: points used only to draw beautiful curves.

Only semantic nodes are interactive or presented as meaningful wishes.

Rendering control points must never appear as unexplained clickable dots, Route IDs, Root IDs or generation labels.

## Selection behaviour

When a semantic node is selected:

- the selected point must be unmistakable;
- the path from the lineage origin to that point should softly iridesce / brighten;
- relevant descendants may remain visible at lower emphasis;
- CONNECT / CARRY warps associated with that lineage can become visible or brighter;
- remote endpoints of those warps can receive subtle radar / echo markers.

This is contextual highlighting, not a permanent renderer redesign.

## Product labels

Remove technical rendering vocabulary from the normal product UI:

- Root A / Root B / etc.;
- Route IDs;
- generation numbers;
- engine node IDs.

If history needs language, use product terms such as Origin, branch, sub-wish, pivot, Bloom, Let go, Help and connection.

## Seed-world rule

The next simulation must no longer take arbitrary graphical nodes and paste unrelated wish texts onto them.

Instead, it must generate coherent wish histories first, then draw those histories using the locked V03 visual language.

Target test population:

- 100 simulated **root wishes**;
- their descendants and history generated from CREATE / PIVOT / SPLIT / nested SPLIT / BLOOM / LET GO;
- a realistic overlapping subset receiving HELP and ENCOURAGE;
- a small number of explicit cross-lineage CONNECT / CARRY warps;
- all simulation clearly marked SIMULATED when surfaced as data.

The categories intentionally overlap. A lineage may pivot, split, receive help and Bloom on different branches.

## Graphical lock

The V03 style remains the source of truth for:

- palette;
- organic line quality;
- halos;
- particles / pulses;
- depth;
- pan / zoom;
- minimap;
- overall performance envelope.

Semantic changes may alter topology because the topology now has meaning. They must not reintroduce the rejected V18-V21 flat / over-dense renderer experiments.

## Non-negotiable governance

- outsiders can propose PIVOT / SPLIT / CONNECT / HELP;
- they cannot impose them when wisher acceptance is required;
- only the wisher can confirm BLOOM or LET GO;
- no HELP or ENCOURAGE threshold can auto-Bloom a wish.

## Versioning

Visual baseline: `VISUAL-V03-LOCKED`

Current product baseline: `PRODUCT-V20`

Next semantic population experiment: `SEMANTIC-V23`

SEMANTIC-V23 must remain isolated from the official route until visual and semantic review is completed.
