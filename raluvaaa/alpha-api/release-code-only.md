## Preconditions and preservation

- The source SHA and Worker SHA-256 must be pinned in the helper and plan. The helper reads Worker bytes from that exact Git object and checks their hash; a later branch tip is never substituted.
- Before upload and immediately before promotion, read-only public GitHub Actions queries reject other active/queued runs of both known Worker deployment workflows. Only the exact current release run ID is excluded. Unrelated workflows are neither blocked nor cancelled; unavailable or incomplete run inventories stop the release.
- Existing Cloudflare credentials are available only to the release step, after credential-free plan validation. The later health step has no credentials. GitHub CI verification is read-only and unauthenticated against this public repository; unavailable or incomplete results block the release.
- The active deployment and latest uploaded version must equal the freshly reviewed baseline. All six existing bindings are inherited by name with `bindings_inherit=strict`. Secret values are never requested or resubmitted. D1 identity, plaintext values and full returned binding metadata are compared internally without logging their values.
- Unknown runtime/settings/binding fields, test authentication, extra triggers, non-default placement, split traffic or configuration drift stop the release. No settings, secrets, triggers, D1 schema or D1 contents are written. This route creates no credentials and changes no plan, payment or paid feature.
- Runtime/settings/triggers are read again before upload, before promotion and after promotion. The documented read-only `annotations.workers/triggered_by` describes the operation that created a version: it is not resubmitted and is excluded only from post-promotion annotation equality. All writable annotations remain exact; pre-upload/pre-promotion metadata drift still blocks. Script `etag` and `last_deployed_from` are descriptive code/origin metadata, not inherited runtime settings; exact uploaded bytes are independently hash-checked. Candidate runtime/bindings must equal baseline metadata. The only mutations are one version upload and one deployment of that exact candidate at 100%.

## Bounded public visibility verification

The helper reads the fixed public WORLD endpoint without authentication, cookies or redirects before its last pre-upload runtime checks and after promotion. Both snapshots must have the expected public response/wish shape and no observable parent cycle. Each snapshot must contain none of the exact five fixture roots, and no wish ID, root ID, lineage ID or parent ID may reference those roots. Any visible chain that reaches a fixture root therefore blocks. The roots are expected to be absent before upload; this is not the previous cleanup transition from visible to hidden.

Every public wish observed before upload is fingerprinted in memory and must remain byte-equivalent after canonical object-key ordering. Changes to content, location, state, timestamps, counters, ownership flag or structural pointers fail closed; deletion also fails. Additional unrelated wishes and response ordering changes are allowed. At the 600-wish limit, a newly visible row displacing a previously observed row is inconclusive and fails, even when legitimate concurrent activity could explain it.

This proves preservation only for the observed public wish rows, capped at 600. It does not prove the contents, ancestry or preservation of unseen D1 rows, nor audit event row contents. Parents outside the observed view are permitted; their ancestry is not proven. A hidden descendant whose ID is unknown and whose family references have all been rewritten cannot be identified by this public check alone. Separate SELECT-only implementation review and local database-preservation tests remain required.

Only aggregate counts are logged: before/after public wishes, absent fixture roots, unchanged observed wishes and additional observed wishes. Snapshots, fingerprints, public text, locations and row IDs remain in memory. Malformed, redirected, unreadable, network-error, authorization-error or quota-error responses stop the release; there is no degraded mode. A failure after promotion retains checkpoints and stops without automatic retry or rollback.

## Concurrency limitation

The Cloudflare deployments API has no documented compare-and-swap condition. Workflow concurrency serializes this workflow only. An external actor can still change configuration between the final read and promotion. The helper checks immediately afterward and fails on detected drift. These checks are not an absolute lock against external changes.

## Checkpoints and recovery

Logs and the job summary retain only safe stage names, aggregate public visibility counts, source SHA, code hash, baseline deployment/version IDs, candidate version ID and the new deployment ID when known. Raw metadata, credential values, variable values and database IDs are excluded.

Never rerun a failed release blindly. An upload or promotion may have succeeded even when its response was lost. Inspect current deployment/latest-version metadata first. If the candidate was only uploaded, it remains undeployed; the original baseline guard deliberately prevents a second upload from inheriting an unreviewed latest version.

Rollback is a separate, reviewed operation, not an automatic failure handler. Before considering it, establish that the candidate is the sole active version, that no subsequent deployment or configuration change occurred, and that the recorded baseline still has the expected bindings/settings. Promote only the recorded baseline version at 100%, without `force`, then verify runtime/settings/triggers and GET `/v1/health`. A rollback must never restore database contents, run schema SQL, rotate secrets, or discard writes made by users. If secret or runtime drift prevents rollback, stop for review rather than forcing it.

After a successful release, the credential-free GET `/v1/health` check proves liveness only. Do not use an authentication or application-data mutation as an automatic production smoke test.
